# Open World release and recovery

The studio parent contains the editor, account token and provider key. Game documents run in an opaque sandbox in both studio previews and direct/shared URLs. The sandbox permits scripts and pointer lock, with CDN access restricted to the game's existing Three.js hosts. Origin storage is unavailable to game code; a bounded, empty in-memory settings store keeps older games working. Cosmetic game settings reset on reload. Server-saved versions remain durable.

The only message accepted from the active game frame opens the public store interface. It carries no URL, credentials, edit operation or account action. Messages from other windows are ignored. Every private session, history, version render, share, publish and suggestion checks its owner. Sharing exposes the selected game and its public description, never its private messages or version list. A guest uses a random 256-bit capability. Existing guest sessions need their original provider key once to migrate. Logged-in ownership cannot be bypassed with a guest key.

Production must provide a stable JWT_SECRET of at least 32 characters and persistent DATA_DIR and VERSIONS_DIR. The base game is kept at DATA_DIR/base.html (or BASE_GAME_PATH). Seed data is disabled unless SEED_DEMO_STORE=1 is explicitly configured. Do not enable demo reseeding on a live installation.

Run one Uvicorn worker and one replica with SQLite. Request rate limits and two concurrent generations are bounded in the application process; introduce a shared limiter before adding replicas. Messages are limited to 8,000 characters, uploaded images to 4MB, request bodies to 8MB, and generated HTML to 4MB. The provider has a 90-second timeout and no automatic retries. Partial/truncated or non-unique patches save no new game version. Game files are written atomically before their database references are committed. A failed version transaction removes only its new file.

At startup, the service verifies a pre-migration snapshot, applies additive schema changes, then verifies a new snapshot. It also snapshots every 12 hours, retaining seven copies under DATA_DIR/recovery with private permissions. Each snapshot contains a consistent SQLite backup, every referenced game file, the current base game and checksums. Startup fails if required game files are missing. Health checks the database, referenced files and backup freshness; failure or a copy older than 48 hours returns HTTP503.

Use `python -m app.backend.recovery verify /private/snapshot.zip` to verify a copy. Restore only into a new empty location with `python -m app.backend.recovery restore /private/snapshot.zip --destination /private/restored --deletions /current/private/deleted-accounts.json`. Point DATA_DIR at the restored directory and VERSIONS_DIR at its versions subdirectory. Restore increments every account's authentication revision and clears all guest proofs, so old account tokens and guest credentials cannot resume restored sessions. Users can sign in again; old guest-only sessions need operator-assisted ownership review. Never overwrite the live volume to test a restore.

A verified encrypted independent copy is retained on the owner's computer. Install the hourly Mac mirror with `python3 ops/install-recovery-mirror.py --project PROJECT_UUID --environment ENVIRONMENT_UUID --service SERVICE_UUID` using an existing authorized Railway login. It keeps its runtime, pinned official CLI, validator, private configuration and encryption key under `~/Library/Application Support/OpenWorld/recovery-mirror`, so background execution does not depend on access to Documents. The pinned CLI4.29 uses the existing authenticated relay; newer CLI SSH/file-transfer commands require separately registered SSH keys. Do not register new access just to work around a missing background PATH.

The mirror checks the transfer checksum, snapshot manifest, freshness and authenticated encryption before retaining up to seven encrypted copies. Each new snapshot also gets an offline restore drill with authentication invalidation and a representative schema change. It preserves the existing encryption key. `status.json` separately records the last successful check, the server snapshot time and the last restore drill; a failed run does not refresh these timestamps. Check the job with `launchctl print gui/$(id -u)/com.openworld.recovery-mirror` and review its private mirror.log/mirror-error.log. Hourly checks require this Mac to be awake and Railway access to remain valid. Server snapshots run every12hours, so the normal awake-machine recovery-point window is about13hours; this is not an always-on independent cloud backup. Retain the encryption key separately when moving the recovery setup. No public backup download or restore endpoint is exposed.

Release checks use disposable SQLite data, synthetic users and browser probes. `python -m unittest discover -s tests -v` checks private access, guest proofs, shared-game isolation, resource bounds, incomplete provider responses, prior-version retention, missing/corrupt recovery data, and restored-session invalidation. The final release also requires an actual provider generation, reload/version switch and explicit share with a QA account. No provider credential or private account data belongs in source, a release archive or logs.

Model policy: normal game edits use Claude Sonnet 5.5 with medium effort. Operators can select Claude Opus 5.5 using OPENWORLD_MODEL for more demanding editing workloads. Retired or unrecognized overrides fall back to Sonnet 5.5. A generation never silently retries on a more expensive model.


## Account data and deletion-aware restoration

The active account export is a private ZIP of the caller's profile, chats, version metadata and owned HTML files. It excludes password/JWT/provider/guest-proof hashes. Exports are prepared under DATA_DIR/exports with private permissions and removed after the response; do not include leftover exports in a manual backup. A user may need operator assistance above the 512 MB safety limit. Costly export/closure actions are capped per authenticated account, separately from shared-address request limits.

Account closure rechecks the current password and exact DELETE confirmation. It holds the publication lock, removes only the caller's records, quarantines unreferenced game files and commits atomically. An ordinary database/file failure restores the rows, files and prior deletion evidence. Before file movement, durable account-ID-only intent is written to DATA_DIR/deleted-accounts.json. A crash after that intent is reconciled before startup snapshots or traffic. The service refreshes its recovery snapshot after closure; health degrades if the deletion evidence is newer than the last snapshot.

**Older recovery archives must never be served without current surviving deletion evidence.** The restore CLI requires `--deletions /current/private/deleted-accounts.json`; retain that file independently with current recovery copies. It is not sufficient to use the older archive's own pre-deletion log. The command merges surviving evidence, purges removed accounts and their game files in the new destination, then invalidates all remaining old sessions. Missing/malformed evidence fails restoration. Restored traffic must use this deletion-aware helper. This prevents an old snapshot from reactivating a removed account. Contact messages are not linked to unverified signup addresses; operator-reviewed contact removal is a separate request.

New snapshots include the deletion evidence in their verified manifest. Existing older snapshots remain verifiable, but restoration requires surviving evidence. Source `ops/mirror-recovery.py` carries the compatible current-snapshot drill. Its legitimate status records restore-contract version2 only after a successful verified check; a missing/older contract, missing prior drill or changed archive forces a fresh restore drill even when an encrypted copy already exists. Before releasing account closure, update the existing mirror's copied `recovery.py` and `sync.py` from these source files while preserving its runtime, config, pinned CLI and encryption key; run its existing private foreground sync once to verify the changed archive/helper. No new credentials or access registration is required. Do not rerun account creation or replace the encryption key. The coordinator performs that existing-runtime rollout.

The seven server snapshots and seven independent encrypted copies rotate separately; copies can outlast deletion if backups stop. The latest surviving evidence must accompany disaster recovery. Retain the minimal removed IDs for that purpose. Redeploying application code must preserve both the live volume and this evidence; a rollback must retain the current deletion-aware restore procedure.
